# Churn Risk API

Predicts which customers are likely to leave, and serves the prediction from an ASP.NET Core API. The model is trained in Python, exported to ONNX and run from C#, with every prediction logged to SQLite for monitoring.

```
Python: clean data -> compare models -> export to ONNX -> schema + test cases
                                             |
C#:     POST /predict -> validate -> run ONNX model -> log to SQLite -> GET /monitoring/summary
```

## Results

Full tables are in [docs/EXPERIMENTS.md](docs/EXPERIMENTS.md), generated by the training script.

- **Data:** IBM's public Telco churn sample, 7,043 customers, 26.5% churned. It is a fictional sample, so these numbers show the method and not a real business.
- **Model:** Logistic Regression, test ROC AUC 0.842, scored once on 1,409 customers.
- **Use:** calling the 20% of customers with the highest scores reaches 50% of the customers who actually churned. In the high-risk band, 71% churned, against 11% in the low-risk band.

## The decision worth reading

Gradient Boosting scored slightly higher in cross-validation (ROC AUC 0.847 vs. 0.846), but its probabilities changed by up to 0.20 once exported to ONNX, on customers it had not trained on. The same check on its own training rows showed almost no difference, so a check on training data alone would have missed it.

A model that changes when exported is not the model that was evaluated, so export accuracy is now a requirement for being chosen. Logistic Regression's exported probabilities stay within 0.0000002 of the trained model. The likely cause for the tree models is 32-bit rounding near split points, but I did not prove that, because a 64-bit export would not load in ONNX Runtime.

## API

| Endpoint | Purpose |
|---|---|
| `POST /predict` | Validates one customer and returns the probability, risk band and model version |
| `GET /monitoring/summary` | Prediction count, risk bands, average latency and a drift alert |
| `GET /health` | Status and loaded model version |

```bash
curl -X POST http://localhost:8080/predict -H "Content-Type: application/json" -d '{
  "SeniorCitizen": 0, "Partner": "Yes", "Dependents": "No", "tenure": 2,
  "PhoneService": "Yes", "MultipleLines": "No", "InternetService": "Fiber optic",
  "OnlineSecurity": "No", "OnlineBackup": "No", "DeviceProtection": "No", "TechSupport": "No",
  "StreamingTV": "No", "StreamingMovies": "No", "Contract": "Month-to-month",
  "PaperlessBilling": "Yes", "PaymentMethod": "Electronic check",
  "MonthlyCharges": 70.7, "TotalCharges": 151.65
}'
```

Bad input gets a 400 that names each bad field. Fields the model does not use are refused, so personal data cannot be sent here by accident. The database stores scores only, never customer details.

The drift alert fires when, after at least 30 predictions, the average score moves more than 0.10 from its value on the training data. It is a simple first signal, not a full drift analysis.

## Run it

```bash
docker build -t churn-risk-api .
docker run -p 8080:8080 churn-risk-api
```

Without Docker, with the .NET 10 SDK:

```bash
dotnet test
dotnet run --project src/ChurnRisk.Api
```

To retrain with Python 3.12:

```bash
pip install -r training/requirements.txt
python training/train.py
```

## Tests

- 25 .NET tests run the real API with the real ONNX model and a real SQLite file. One test checks that C# returns the same probability as scikit-learn on 25 customers.
- 7 Python tests cover the data cleaning rules.
- CI runs both, then builds the Docker image, starts it and sends it a real prediction.

## Limits

This is a portfolio project. It has no authentication, and SQLite suits one instance only. A real deployment would need both solved, along with retraining on real data and a fuller drift check.
